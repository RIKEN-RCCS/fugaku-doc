4.4. Login¶

Loggin to to the Fugaku by using local account, logging to login node with using SSH Version2 (Publick key authentication).

Create an SSH key pair (public key and private key) on the user terminal in advance and register the public key from the Fugaku website screen. Register only the public key. When a private key is registered, processing such as temporary suspension of login may be performed as a security measure.

Note

If you change the permissions of the following directories and files under the home directory of the login node, you will not be able to login using ssh.

  • home directory permission (700)

  • ~/.ssh directory permission (700)

  • ~/.ssh/authorized_keys permission (600)

Please do not change these permissions. For details, please refer to “Directory and File Permission Management“.

4.4.1. Private key/Public key creation¶

To use the Fugaku, create the pair of private key and public key on the user device. Recommended creating type is from following.

  • Ed25519

  • ECDSA (NIST P 521)

  • RSA (Key long more than 2048bit) : For how to use RSA keys, refer to “Operation change regarding ssh access to login nodes” on the Fugaku website.

This section describes the procedure for creating key pair of Ed25519 (public / private keys) using UNIX / Linux (OpenSSH) and Windows (puttygen). To use puttygen, it is necessary to install the terminal emulator PuTTY (patty) in advance.

  • Unix/Linux/Mac (OpenSSH)

  • Windows (PuTTYgen)

4.4.1.1. Unix/Linux/Mac (OpenSSH)¶

Execute a command ssh-keygen on the user’s device, create a private / public key pair.

  1. Start terminal and execute a command ssh-keygen.

  • If Mac(OS X), start Terminal(Application ‣ Utility ‣ Terminal) and execute a command ssh-keygen.

  • If UNIX/Linux, start terminal emulator and execute a command ssh-keygen.

[terminal]$ ssh-keygen -t ed25519
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/username/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):  # Enter passphrase
Enter same passphrase again:                 # Re-enter the same passphrase
Your identification has been saved in /home/username/.ssh/id_ed25519.
Your public key has been saved in /home/username/.ssh/id_ed25519.pub.
The key fingerprint is:
SHA256:khbWyIyUqMnyjK1Ok78l8EivKbQLNgP3vyhjYBgvif8 namehostname
The key's randomart image is:
+--[ED25519 256]--+
|   ...           |
|  ...+ o         |

|=@    + S        |
|@o%  . .         |
|=%.= .           |
|*=O =            |

Note

  • Set a passphrase that is difficult for others to guess, just like a password. Please be sure to set a passphrase. We recommend a passphrase length of at least 15 characters.

  1. Once execute ssh-keygen, two types are created: a private key (id_ed25519) and a public key (id_ed25519.pub) on .ssh directory under the home directory.
    Register the public key (id_ed25519.pub) using the Fugaku website.

4.4.1.2. Windows (PuTTYgen)¶

Create a private / public key that can be used with PuTTY / WinSCP with puttygen.

  1. Start puttygen.
    Select “EdDSA” for type of key and select “Ed25519 (255 bits)” to generate, then click “Generate”.

  1. Move the mouse cursor randomly.

  1. Save the public key.
    Copy the displayed contents on “Public key for pasting in to OpenSSH authorized_keys file:” to the clip board (It is recommended to paste on the notepad).
    The contents pasted on the clip board (Public key) is registered with using the Fugaku website.

  1. Input a passphrase to both “Key passphrase” and “Confirm passphrase”. After inputting, click “Save private key” and save the private key. Remember to enter your passphrase when you log in to the login node.

Attention

Set a passphrase that is difficult for others to guess, just like a password. Please be sure to set a passphrase. We recommend a passphrase length of at least 15 characters.

  1. Input a file name for storing the private key to “File name(N)”, click “Save(S)”. The private key is stored.

4.4.2. Public key registration¶

  • Registration using Fugaku website

  • Additional registration of public key

4.4.2.1. Registration using Fugaku website¶

  1. Log in to the Fugaku website(https://www.fugaku.r-ccs.riken.jp/en), then click [User Portal] from menu.

  1. Click [Publickey registration] from menu.

  1. Copy and paste the public key to be used to “Publickey registration” area.

  1. Click [Registar]then register.

  2. Confirm the content and click on [Register].

  1. When the “Registration has been Completed.” screen appears, the public key registration is complete.

Note

Only one public key can be registered per operation. For the second and subsequent operations, additional registration is required. If you want to register two or more public keys, repeat the same operation.

  1. If the public key is incorrect, an error message will be displayed. Check the public key and execute the registration process again.

4.4.2.2. Additional registration of public key¶

This section describes the procedure for registering additional public keys in the login node.
There are a method of registering additionally using the Fugaku website and a method of editing the file directly by logging in to the login node. This section shows how to edit a file on the login node.

  1. Edit ~/.ssh/authorized_keys on login node.

[_LNlogin]$ vi  ~/.ssh/authorized_keys


Press [i] key to enter vi editor insert mode.
Click the right mouse button and paste the contents of .ssh / id_rsa.pub.

Press the [esc] key, enter [wq!], and press the [Enter] key.

  1. Change permission of private key registered authorized_keys.

[_LNlogin]$ chmod  600  ~/.ssh/authorized_keys

4.4.3.4. Arm login node¶

The Arm login node is a login node with an Armv8-based Arm processor.

The Arm login node is logged in via the normal login node with Intel CPU. Users cannot log in directly to the Arm login node from the Internet.

Please execute ssh arm1 on the login node to log in. The host-based authentication is used for the connection between the login node and the Arm login node, so authentication by users is not required .

[_LNIlogin]$ ssh arm1
Last login: XXX MMM DD HH:MM:SS 2020 from 10.4.254.NN
[_LNAlogin]$

The Arm login node is configured as follows:

  • home area and data area are common to other login nodes. However, NFS mount is used.

  • Commands such as pjsub and pjstat are not available.

  • Provides direct Internet access. Proxy setting is not required.

  • The Arm compiler and LLVM10.0.0 (build with asis) is installed.

  • When using the compiler, check the module file by executing module avail and set the environment settings properly.

4.4.4. File transfer method¶

Files can be transferred via the login node using the file transfer program (scp / sftp) installed on the user terminal. You can use login.fugaku.r-ccs.riken.jp for transfer.
Use of protocols (ftp / r commands) that are vulnerable to security is prohibited.
For file transfer, the procedure for “ Private key/Public key creation“ must be performed, and the public key must be registered on the login node.

  • File transfer (sftp)

  • File transfer (scp)

  • Windows (WinSCP)

4.4.7. Directory and File Permission Management¶

The permissions of the following directories and files under the home directory of the login node are set to specific values to ensure security.

  • Home directory permissions: 700 (rwx------)

  • ~/.ssh directory permissions: 700 (rwx------)

  • ~/.ssh/authorized_keys file permissions: 600 (rw-------)

These permissions should not be changed.
Using some commands (especially the rsync -a command) may unintentionally change these permissions, which can result in being unable to log in via SSH.
Below, we provide detailed information on the specific behavior of the rsync -a command, which requires particular attention, and safe usage methods to prevent unintentional permission changes.

  • Details and Precautions for rsync -a command

  • Safe Usage of rsync -a Command

4.4.7.1. Details and Precautions for rsync -a command¶

The rsync command is a powerful tool for efficiently copying and synchronizing files and directories.
The -a (archive) option, in particular, is often used for complete data synchronization, as it preserves directory attributes such as permissions, timestamps, and groups as much as possible during transfer.
Although it is recommended for use on Fugaku due to its low overhead, special attention is required as the specific behavior of the -a option can unintentionally alter attributes of parent directories.
Causes of Unintentional Directory Attribute Changes:
The behavior of the rsync -a command differs significantly depending on whether the source path ends with a slash (/) or not.
  • When the source path ends with a slash (/):
    The contents of the source directory are transferred to the destination directory.
    In this case, the attributes of the destination directory itself (e.g., permissions) are overwritten with the attributes of the source directory.
    This behavior is due to the synchronization of directory contents, where the destination directory’s attributes are also made to match the source’s.
  • When the source path does not end with a slash (no /):
    The source directory itself is created as a new directory under the destination directory, and its contents are transferred into it.
    In this case, the attributes of the source directory itself are inherited by the newly created directory, but the attributes of the existing destination directory remain unchanged.

Failure to understand this difference in behavior can lead to problems such as unintentionally changing the permissions of important directories (e.g., your home directory), making it impossible to log in.

Command Examples and Behavior Comparison:

Command Example

Trailing ‘/’ in Source Path

Behavior

$ rsync -a /path/dir/ /path/dest

Yes (/)

The contents (files and subdirectories) of /path/dir are copied to /path/dest. The attributes of /path/dest itself are overwritten with the attributes of the source /path/dir. (Effectively, /path/dest attributes are synchronized with /path/dir)

$ rsync -a /path/dir /path/dest

No

The /path/dir directory itself is copied under /path/dest, creating /path/dest/dir. The directory attributes of the newly created dir retain their original state, and the attributes of the existing /path/dest directory remain unchanged.

4.4.7.2. Safe Usage of rsync -a Command¶

To avoid the risk of unintentionally changing permissions of important directories (especially the home directory), we recommend the following safe usage methods for the rsync -a command.
When transferring data to your home directory, do not transfer it directly into the home directory itself. Instead, create an intermediate directory for storing data (e.g., ~/data_transfer) in advance, and transfer the data into that intermediate directory.
Safe Execution Example:
[_LNlogin]$ rsync -a /volXXXX/data/hpXXXXXX /volXXXX/mdtX/home/uXXXXX/data_transfer

  • In this example, an intermediate directory for data transfer (data_transfer) is created in advance under /volXXXX/mdtX/home/uXXXXX.

  • The rsync command copies the /volXXXX/data/hpXXXXXX directory itself under /volXXXX/mdtX/home/uXXXXX/data_transfer. As a result, /volXXXX/mdtX/home/uXXXXX/data_transfer/hpXXXXXX is created.

  • Even if the source path includes a trailing slash (/), only the attributes of the intermediate directory (data_transfer) are affected, thus avoiding the risk of changing home directory permissions.

NG Execution Example:
[_LNlogin]$ rsync -a /volXXXX/data/hpXXXXXX/ /volXXXX/mdtX/home/uXXXXX

  • In this command, because the source path /volXXXX/data/hpXXXXXX/ has a trailing slash (/), the contents of /volXXXX/data/hpXXXXXX are transferred to the destination /volXXXX/mdtX/home/uXXXXX (the user’s home directory).

  • In this process, the permissions of the home directory /volXXXX/mdtX/home/uXXXXX will be overwritten with the permissions of the source directory /volXXXX/data/hpXXXXXX.

  • If the home directory’s permissions are changed from 700 to something else, it will have a fatal impact on system usage, such as making SSH login impossible.

Pre/Post-Confirmation of Attribute Changes:
When performing data transfers, always check before and after command execution to ensure that no important directory attributes have been unintentionally changed.
An example command to check home directory attributes and their default state is shown below:
[_LNlogin]$ cd
[_LNlogin]$ ls -ld .
(Default example: drwx------ 24 uXXXXX fugaku 4096 Aug 26 12:05 .)
If the permissions are anything other than drwx------, the state is not appropriate.

Note

Troubleshooting: If Home Directory Permissions are Changed

  • If you are still able to log in, use the chmod command to correct the permissions to the appropriate state (700).

    How to get the full path of your home directory:
    [_LNlogin]$ readlink -f $HOME
/volXXXX/mdtX/home/uXXXXX
[_LNlogin]$
    Example of chmod command execution:
    [_LNlogin]$ chmod 700 /volXXXX/mdtX/home/uXXXXX
[_LNlogin]$

  • If you are unable to log in, you cannot resolve the issue yourself. Please contact the Fugaku support website immediately.
